# 測試規格

> 狀態：初稿（2026-10-26）。
> 本文件說明測試怎麼分層、怎麼標註，以及每條驗收條件由哪一層驗證。測試案例本身寫在程式碼中，不在此重抄。

## 0. 範圍與邊界

**本文件管**：測試分層、追溯方式、測試資料來源、每條 PRD 驗收條件的驗證層級。

**本文件不管**：預期值本身。公式的預期值在 [`calc.md`](calc.md) 的範例表；行為的預期在 PRD 驗收條件。

---

## 1. 測試分層

| 代號 | 層 | 工具 | 內容 | 外部依賴 |
|---|---|---|---|---|
| **U** | 引擎單元測試 | pytest | `engine/` 的純函式：公式、狀態、排序、登記表狀態機 | 無 |
| **S** | 來源解析測試 | pytest | `sources/` 解析錄好的真實回應；完整性檢查 | 錄製的回應檔 |
| **P** | 流程整合測試 | pytest | `jobs/` 用暫存 SQLite、假來源、固定時鐘跑完整流程 | 無 |
| **X** | 輸出契約測試 | pytest + JSON Schema | `latest.json` 符合 [`data-model.md`](data-model.md) §6；CLI `--json` 輸出符合 §7；重複產生位元組相同 | 無 |
| **F** | 前端單元測試 | Vitest | 格式化、顏色、搜尋比對、排序切換、新鮮度 | 無 |
| **E** | 端對端測試 | Playwright | 以固定的 `latest.json` 啟動網站，驗證畫面與互動 | 無 |
| **M** | 人工檢查 | 檢查清單 | 無法自動判定的項目 | — |

- **TEST-1** U、S、P、X、F、E 全部在 CI 中執行，不連任何外部網路。網路存取在測試中預設封鎖，意外的外部請求視為失敗。
- **TEST-2** 時間一律注入：後端傳入 `now`，前端以可替換的時鐘取得現在時間。測試不得依賴真實時鐘。
- **TEST-3** 另有一組**線上冒煙測試**（標記 `live`），對真實 API 各打一次、驗證解析不出錯，只在手動或每週排程執行，不擋 CI。用途是及早發現外部 API 改版。

## 2. 追溯方式

- **TEST-TRACE-1** 每個測試以標記註明它驗證的條文：pytest 用 `@pytest.mark.req("F2-AC4", "CALC-APY-1")`；Vitest 與 Playwright 在測試名稱開頭寫 `[F6-AC11]`。
- **TEST-TRACE-2** 腳本 `scripts/trace.py` 掃描所有測試的標記，產生「條文 → 測試」對照表，並在 CI 中檢查：
  - 每一條 `F*-AC*`、`NFR-AC*`、`CALC-*`、`DATA-CLI-*` 至少有一個測試，或列在 §5 的人工檢查清單中。`DATA-CLI-*` 納入的理由：CLI 是同機 agent 依賴的對外契約，與 `latest.json` 同等重要，卻沒有對應的 PRD 驗收條件。
  - 標記中引用的條文編號都存在於文件中（防止引用已改號或打錯的條文）。
- **TEST-TRACE-3** 對照表由腳本產生，不手寫在本文件中；本文件 §4 只規定每條驗收條件的**驗證層級**。

## 3. 測試資料

- **TEST-DATA-1** **錄製的回應**：每個外部來源至少錄一份真實回應，存於 `backend/tests/fixtures/sources/{source}/`，檔名含錄製日期。包含特殊案例：xStocks 缺交易所欄位的代幣（`PDDx`）、`isTradingHalted` 的代幣、包裝地址；Ramses 池名費率與鏈上不符的池子。
- **TEST-DATA-2** **合成資料**：狀態、排序、登記表狀態機一律用最小的合成資料，每個測試只放必要的池子與快照，使預期值一眼可見。
- **TEST-DATA-3** **計算範例**：[`calc.md`](calc.md) §5 的範例表 E1～E8 必須逐一成為測試。
- **TEST-DATA-4** **參考專案的測試**：移植數學模組時一併移植，年化天數不同處調整預期值並註明。
- **TEST-DATA-5** **鏈上解碼驗證**：每種集中流動性池解碼器，至少一個錄製的帳戶或合約回應，驗證以 √P 算出的價格與同時錄下的 GeckoTerminal 價格比值在 0.98～1.02（SRC-SOL-5）。
- **TEST-DATA-6** **前端固定資料**：`frontend/tests/fixtures/latest.json` 涵蓋情況 A、B、C 的卡片，以及每一種池子狀態、近似值、股票配股票池、多費率階梯；由後端 X 層測試產生並檢查是否符合 schema，確保前後端用的是同一份契約。
- **TEST-DATA-7** **排序共用案例**：`shared/ranking_cases.json` 收錄多組「池子資料 + 現在時間 → 預期卡片分類、最佳池子、排行順序」，後端 U 層與前端 F 層讀同一份檔案測試，確保兩邊的排序實作一致（UI-FRESH-6）。至少包含：平手的次要排序、情況 B 的主要原因平手、股票配股票池、全部池子在前端轉為過期、主要狀態為「官方已下架」或「無法計算」的池子在前端轉為過期後主要狀態不變（過期列為次要）。
- **TEST-DATA-8** **拆股**：股價序列在資料庫中已有 90 天未拆股的 K 線，增量回應中重疊日的價格已按 1 拆 10 改寫。驗證：觸發整個窗口重抓（SRC-YF-6），重抓後算出的 σ 與「從頭以還原後序列計算」相同，且不出現虛假的跳空。另驗證沒有重疊日期時同樣觸發重抓。

### 非功能需求

| 條文 | 層 | 驗證方式 |
|---|---|---|
| NFR-AC1 | M、CI | CI 跑秘密掃描（例如 gitleaks）；人工確認 `.env` 內容 |
| NFR-AC2 | E | 記錄頁面載入與操作期間的所有請求，網域只能是本站與流量統計 |
| NFR-AC3 | P | 先以正常資料跑一輪並匯出；再讓單一來源拋錯跑下一輪。驗證：其他來源的資料照常更新；失敗來源相關的卡片、池子與最後一次成功的數值仍保留在 `latest.json`（只依新鮮度標示），沒有被清空或移除 |
| NFR-AC4 | P | 來源失敗數輪後恢復，下一輪資料正常更新，無需任何操作 |
| NFR-AC5 | P | 彙整前後，以同一批資料計算的每日 TVL 平均與日 APY 相同；資料含回補日與斷線日（近似日），彙整後的日 APY 與近似標記也相同（DATA-STORE-3） |
| NFR-AC6 | E | 360px 寬度下 `scrollWidth ≤ clientWidth` |
| NFR-AC7 | F | ESLint 規則禁止範本中出現未經語系函式的文字 |

| NFR-AC10 | P | 每次工作在 `runs` 留下完整欄位 |
| NFR-AC11 | P、M | P：備份檔可開啟並通過 `integrity_check`、筆數一致；M：每月實際還原一次 |

### CLI 資料介面（工程契約，無對應的 PRD 驗收條件）

| 條文 | 層 | 驗證方式 |
|---|---|---|
| DATA-CLI-1 | X | 三個指令加 `--json` 時，stdout 可整份解析為 JSON 且沒有其他內容；資料庫不存在、參數錯誤時結束碼分別為 1、2，stdout 為空，錯誤只在 stderr；查無資料時結束碼 0、`items` 為 `[]` |
| DATA-CLI-2 | X | 輸出符合 JSON Schema（外層與三種 `items`）；所有欄位都存在，沒有值者為 `null`；同樣的資料庫與參數兩次輸出的 `items` 相同 |
| DATA-CLI-3 | X | Schema 中的 `schema_version` 與程式常數一致（改動 schema 而未升版時測試失敗的機制，實作時以 schema 快照比對） |
